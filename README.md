## Description

The primary goal of this repository is to provide an automated, streamlined workflow for setting up a fully configured Agentic Test Workspace. Instead of manually assembling configuration files, tools, and best practices, this repository includes an interactive setup script that automatically prepares your entire workspace environment. When you run the setup script, it automatically performs the following actions:

- **Fetches Agentic Test Skills**: Downloads the latest Menditect and Mendix agentic testing skills (from Menditect/agentic-test-skills) to equip your AI assistant with testing best practices, naming standards, and workflow rules.
- **Installs & Configures Menditect Marketplace Modules Automatically**: Detects whether the **MTA Plugin (`MtaPluginModule.mxmodule`, Marketplace ID `214717`)** is installed and configured in your Mendix project. If missing or unconfigured, it automatically downloads the compatible Mendix 9, 10, or 11 version from the Mendix Marketplace, configures all 7 `MtaPluginModule.*` constants, and wires `MtaPluginModule.ASU_Setup_Connection_MTA` into your project's `AfterStartup` microflow. For paid MTA Server licenses, it also installs **Menditect Mx Frontend TestKit (`206637`)**, **Menditect Playwright Connector (`214764`)**, **Menditect MTA Commons (`254123`)**, and downloads the matching **Playwright Driver Bundle JAR (`driver-bundle-<version>.jar`)** into `userlib/`.
- **Configures Model Inspection Tools (mxcli)**: Sets up mxcli (or prepares Studio Pro MCP integration) so your AI assistant can safely inspect microflows, domain models, and decision logic in a read-only manner.
- **Prompts for Required Input Fields**: Interactively prompts you to enter key project-specific details, such as: Your MTA Server URL. An identification token for a service account generated by an MTA Service Account Manager. The local path or repository details for your App Under Test (AUT). Target environment settings.
- **Generates the Agentic Workspace**: Bundles all collected inputs, agentic skills, and MCP server configurations into a ready-to-use workspace tailored specifically to your Mendix application.

Once the script finishes running, it outputs a complete, isolated Agentic Workspace. Opening this workspace folder in your AI assistant enables immediate end-to-end test case generation, test suite setup, and assertion configuration in MTA.

### Use cases

#### 1. AI-Assisted Test Automation in MTA
- **Overview:** Enables AI assistants (e.g., Antigravity/Gemini, Cursor, Claude Code, GitHub Copilot) to design, build, execute, and maintain automated test suites and test cases directly within the Menditect Test Automation (MTA) platform.
- **Key Capabilities:**
  - Automated creation and configuration of test suites, test cases, and test steps.
  - Deep model-driven test design by inspecting Mendix domain models, microflows, and decision logic (via `mxcli` or Studio Pro MCP).
  - Persistent Execution Plan management (`EP_*.md`) and test result analysis.
- **Prerequisites:** Requires an active **MTA License** and an identification token for a service account with *Primitive Tools* enabled on your MTA server.

#### 2. In-Memory Exploratory Testing (Runtime Plugin)
- **Overview:** Enables real-time, sub-second exploratory testing and interactive debugging directly against a running Mendix application instance.
- **Key Capabilities:**
  - Direct execution and testing of Mendix microflows in memory.
  - Live inspection and verification of runtime entity states and data attributes.
  - Instant feedback loops during active development without requiring round-trips to the central MTA web portal.
  - High-velocity 1-turn execution with automatic transaction rollback (`exploratory_execution_mode: "auto_execute"`).
  - Universal Execution Plans (`EP_*.md`) persisted to disk for full test auditability and instant promotion to permanent MTA test suites.
- **Prerequisites:** Requires the **MTA Runtime Plugin** installed and running inside your Mendix application, connected via the local MTA Plugin MCP endpoint (`/plugin/mcp`).

### What is an Agentic Test Workspace?

An **Agentic Test Workspace** is a dedicated project environment created specifically for your **AI coding assistant / agent** (such as Cursor, VS Code with GitHub Copilot/Cline, Claude Code, or Antigravity/Gemini). 

Think of this workspace as the AI agent's dedicated command center containing:
- **Agent Directives & Skills (`skills/`)**: Authoritative testing instructions and domain skills (synchronized from `Menditect/agentic-test-skills`) that teach the AI how to design, write, and execute MTA tests following Menditect standards.
- **MCP Server Configurations (`mta`, `mta_plugin`, `StudioPro`) & Linter Engine (`tools/mta-lint.mjs` / `mta-linter` Studio Pro Extension)**: Standardized Model Context Protocol (MCP) bridges allowing the AI to interact with the MTA Cloud portal, local runtime plugins, and Mendix Studio Pro, paired with the deterministic `mta-lint.mjs` verification engine (executed via CLI in external AI IDEs or via the bundled `mta-linter` Studio Pro Web Extension inside `Menditect_AgenticTestSkills.mxmodule` for MAIA on Mendix 11.12+).
- **Model Inspection & Search Index (`mxcli`, `.mxcli/catalog.db`)**: Fast offline search tools allowing the AI to inspect and understand your Mendix domain models, microflows, and dependencies.
- **Test Artifacts (`menditect-output/execution-plans/`)**: Persistent Menditect test execution plans (`EP_*.md`), gate ledgers (`.mta-gate-ledger.json`), test results, and trace logs—cleanly separated from Mendix MAIA application build plans (`maia/plans/`).

## Prerequisites

> **Best Practice:** You should create a dedicated Agentic Test Workspace for each individual Mendix Application Under Test. Rather than attempting to reuse a single workspace across multiple Mendix applications, clone or instantiate this repository template separately for every Mendix app you intend to test.

Before starting, ensure you have:

- **[Node.js](https://nodejs.org/) (v18+)** installed (required to run the setup script and local MCP proxies).
- **[Git](https://git-scm.com/)** installed (used to sync upstream testing skills).
- Access to MTA with an identification token for a service account (with Call MCP primitive tools: Enabled)
- A local Mendix application under test
- For exploratory testing **[MTA Plugin](https://documentation.menditect.com/installation/import-plugin)** must be installed and connected with MTA.

> [!IMPORTANT]
> **Close Mendix Studio Pro Before Adding or Updating Modules:**
> Ensure your target Mendix project is **closed in Mendix Studio Pro** before running `npm run setup`, `npm run update`, or `npm run update:modules`. When the project is open:
> 1. **File Locks:** Studio Pro and the Java Virtual Machine hold active locks on `.mpr`, `userlib/*.jar` (e.g. `mta-plugin-*.jar`), and `deployment/`, which can cause downloads or directory cleanup to fail with permission errors (`EBUSY`/`EPERM`).
> 2. **In-Memory Cache Overwrite & Data Loss:** Studio Pro caches the project model in memory. If `mxcli` injects constants or updates settings in `.mpr` while Studio Pro is open, saving in Studio Pro (`Ctrl+S` or running the app) will overwrite `.mpr` from its in-memory cache, silently erasing all newly configured MTA constants and configurations!
> 3. **No Hot-Reload:** Studio Pro does not detect updated `.mxmodule` packages on disk until the project is closed and re-opened.
>
> The setup script and update tooling actively detect open Studio Pro sessions (via `<project>.mpr.lock` and active process inspection) and offer interactive options to re-check after closing, proceed with risk, or skip module operations.

### 1. Create your base directory and clone the repository

Create a folder on your local disk and clone `agentic-test-workspace`:

```bash
# Create your base directory (replace 'C:\projects\menditect' with your preferred path)
mkdir C:\projects\menditect
cd C:\projects\menditect

# Clone the central agentic-test-workspace repository
git clone https://github.com/Menditect/agentic-test-workspace.git
cd agentic-test-workspace
```

### 2. Run the setup wizard

Inside `agentic-test-workspace`, run:

```bash
npm run setup
```

The interactive wizard guides you through configuration in a few steps:

- **Workspace Location Strategy**: Choose `[1] Central Tools Hub` (and specify your lightweight app workspace folder, e.g. `../my-app-workspace`), `[2] Standalone Subfolder Workspace`, or `[3] Direct Mendix Project Workspace`.
- **Mendix Model Detection**: Locates your Mendix `.mpr` file, detects Studio Pro version (Mendix 9, 10, or 11), and downloads `mxcli`.
- **Automated MTA Plugin & Marketplace Module Setup**:
  - **MTA Plugin (`MtaPluginModule.mxmodule`, ID `214717`)**: If `MtaPluginModule.mxmodule` is not detected in `<projectDir>/modules/` (or if its constants are not yet configured), the wizard downloads the latest version matching your Mendix major version (9, 10, or 11) via `mxcli`, prompts for `ApplicationInstanceToken` (license key / instance token), `MTAConnectionUsername` and `MTAConnectionPassword` (provided in your welcome email for Free Exploratory users, or under **App > Instances > Details** in the MTA portal for Paid users), `MTAConnectionUrl` (`wss://services.menditect.com` for Free Exploratory or `wss://<your-mta-server>` for Paid MTA), `EnableMcpServer` (`True`), and `McpServerAccessToken`, automatically configures `ConnectionMethod = 'AfterStartup'`, and configures `MtaPluginModule.ASU_Setup_Connection_MTA` on your project's `AfterStartup` microflow.
  - **Paid MTA Add-on Modules & Playwright Driver Bundle**: If a paid MTA server is configured, the wizard also downloads the compatible Mendix 9/10/11 versions of **Menditect Mx Frontend TestKit (`206637`)**, **Menditect Playwright Connector (`214764`)**, and **Menditect MTA Commons (`254123`)** into `modules/`, and downloads the matching **`driver-bundle-<version>.jar`** into `userlib/`.
  - **MAIA Add-on Module (`Menditect_AgenticTestSkills.mxmodule`, ID `305457`)**: When configuring a Direct Mendix Project Workspace (Mendix 11.12+), the wizard automatically downloads and imports `Menditect_AgenticTestSkills.mxmodule` into `modules/`, extracts the skills into `skillssource/_modules/menditect_agentictestskills/`, creates/updates `skillssource/AGENTS.md` and `AGENTS.md`, and creates `menditect-output/execution-plans/`.
- **Model Inspection Source**: Lets you select between `mxcli` (standalone offline engine) or `Studio Pro MCP` (live IDE integration), while using `mxcli` in the background for project analysis.
- **MTA & Instance Setup**: Scans your project for existing MTA application instances, configures connection settings, and isolates secrets into the workspace's `.env` file.
- **Exploratory Execution Strategy**: Select your preferred AI velocity (`exploratory_execution_mode`). Choose `auto_execute` (default) for instant 1-turn test feedback (< 3s total latency) with plan generation and JVM rollback, or `prompt_approval` to require explicit plan sign-off at Checkpoint 1 before running.
- **Skills & AI Scaffolding**: Downloads the latest test skills (`Menditect/agentic-test-skills`) and generates IDE configuration files (`.vscode/mcp.json`, `.cursor/mcp.json`, `.claude/settings.json`, and agent directives) in your target workspace.
- **Optional Code Indexing**: Offers to build a local project catalog (`.mxcli/catalog.db`) for deep code search and dependency analysis.

> [!TIP]
> **Wizard Navigation**:
> - Press **[Enter]** to accept the detected/default value in brackets `[value]`.
> - Type **`b`** or **`back`** at any prompt to return to the previous question and change your answer.
> - A numbered **Configuration Summary & Review** is presented before any files are saved, allowing you to review and jump directly to any setting to edit it.

* **MTA Runtime Plugin Server (`mta_plugin`):**
  - **Endpoint / URL:** Value of `plugin_mcp_url` (e.g. `http://localhost:8081/plugin/mcp`)
  - **Headers:** `Authorization: <PLUGIN_MCP_TOKEN>` *(if configured)*
* **Studio Pro MCP Server (`StudioPro` - optional):**
  - **Endpoint / URL:** Value of `studiopro_mcp_url` (e.g. `http://localhost:7782/mcp`)

## Switching Between Workspace Setup Models

You can switch an existing workspace from any setup model (`[1]`, `[2]`, or `[3]`) to another at any time without losing your MTA settings, credentials (`.env`), or Execution Plans (`menditect-output/execution-plans/`).

Simply run `npm run setup` inside `agentic-test-workspace`. The setup wizard automatically detects and pre-populates your existing `mta_config.json` and `.env` values so you can press **[Enter]** through all connection settings and only change your **Workspace Location Strategy**.

### Scenario A: Switching from `[2] Standalone Subfolder` $\rightarrow$ `[1] Central Tools Hub`
If you previously cloned `agentic-test-workspace` inside a single app workspace and want to convert it to the Central Tools Hub model:
1. *(Optional)* If you want to move the `agentic-test-workspace` folder to a shared parent directory first, move it using your OS file explorer or terminal.
2. Open a terminal in `agentic-test-workspace` and run:
   ```bash
   npm run setup
   ```
3. Select **`[1] Central Tools Hub — Multi-App / Shared Engine`** and enter the path to your existing app workspace folder.
4. Confirm the summary. The wizard will:
   - Update `mta_config.json`, IDE MCP configs, and agent directives (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`) to point directly to the central hub's `skills/` and `tools/`.
   - Prompt to **automatically remove the redundant local `skills/` and `tools/` copies** from your app workspace while keeping `menditect-output/` and `.env` intact.

### Scenario B: Switching from `[1] Central Tools Hub` $\rightarrow$ `[2] Standalone Subfolder`
If you want to decouple a linked app workspace from the central hub so it has its own isolated version of `skills/` and `tools/`:
1. Ensure `agentic-test-workspace` is located inside your app workspace folder (or clone a copy there), and run `npm run setup`.
2. Select **`[2] Standalone Subfolder Workspace — Single-App Isolated`**.
3. Confirm the summary. The wizard will copy `skills/`, `tools/`, and the full `AGENTS.md` orchestrator locally into the workspace and update `mta_config.json` (`workspace_type: "clone_root"`).

### Scenario C: Switching Between External Workspace (`[1]` or `[2]`) $\leftrightarrow$ `[3] Direct Mendix Project`
- **From `[3] Direct Mendix Project` $\rightarrow$ `[1]` or `[2]`:**
  1. Run `npm run setup` in `agentic-test-workspace` and select **`[1] Central Tools Hub`** (or **`[2] Standalone Subfolder`**).
  2. When prompted for your Mendix `.mpr` path, point to your Mendix project folder. The wizard automatically reads your existing settings from the Mendix project's `mta_config.json` and `.env`.
  3. Upon completion, the wizard offers to **automatically migrate `menditect-output/` (including all `EP_*.md` execution plans)** into the new external workspace and clean up the old `mta_config.json`, `.env`, `skills/`, and IDE MCP files from your Mendix `.mpr` directory so your Mendix Git status is clean.
- **From `[1]` or `[2]` $\rightarrow$ `[3] Direct Mendix Project`:**
  1. Run `npm run setup` in `agentic-test-workspace` and select **`[3] Direct Mendix Project Workspace`**.
  2. If an external workspace was previously configured, the wizard offers to **copy your existing `menditect-output/` execution plans** directly into the Mendix project folder.

## Synchronization & updates

The workspace includes a version inspection mechanism that queries GitHub releases (`mendixlabs/mxcli`) and repository skill frontmatters (`Menditect/agentic-test-skills`) to compare local versions against remote versions before prompting the user to confirm.

> [!NOTE]
> The MTA testing skills (`skills/`) and the MTA linter engine (`tools/mta-lint.mjs`) are tightly coupled. Whenever you run `npm run update:skills` (or `npm run update`), the linter tools and test fixtures are automatically synchronized in lockstep with the skills so that test plan validation and smoke audit rules always match the latest skill definitions.

```bash
# Synchronization & Updates
npm run update:check       # Check versions without downloading (Dry Run)
npm run update             # Interactively update all components (skills + linter tools + mxcli + Marketplace modules)
npm run update:skills      # Update MTA testing skills and coupled linter tools (skills/ + tools/)
npm run update:mxcli       # Update mxcli binary only
npm run update:modules     # Update Menditect Mendix Marketplace modules (.mxmodule) & Playwright driver-bundle JAR only
npm run update -- --yes    # Auto-approve available updates (non-interactive / CI)
npm run update -- --force  # Force re-download/re-sync even if up to date

# Verification & Diagnostics
npm run verify             # Verify active workspace MCP connectivity, catalog, and agent directives
npm run verify -- <path>   # Verify a specific linked app workspace (e.g. npm run verify -- ../app-alpha)
npm run lint:test          # Run the 87-check mta-lint.mjs self-test suite

# Running from Workspace Root (when agentic-test-workspace is in a subdirectory)
npm run --prefix ./agentic-test-workspace update
npm run --prefix ./agentic-test-workspace verify
```

## Workspace Verification & Diagnostics

The workspace includes a built-in diagnostic and health-check engine (`scripts/verify-setup.js`) that validates your environment configuration, schema compliance, security hygiene, and live MCP connectivity to MTA and the MTA Plugin.

### Running Updates from the Central Tools Hub (`agentic-test-workspace`)

Just like `npm run verify`, when working in the **`[1] Central Tools Hub`** architecture, `npm run update` and `npm run update:modules` automatically detect which workspace settings to update using the discovery pipeline:

1. **Update Default / Active Workspace:**
   ```bash
   npm run update            # Updates skills, mxcli, and marketplace modules for the active workspace
   npm run update:modules    # Updates only Marketplace modules & Playwright driver jar for the active workspace
   ```
   If a single linked workspace is detected, it is updated directly. In environments with multiple registered workspaces, running without path arguments updates the primary active workspace.

2. **Update a Specific Workspace via CLI Argument:**
   You can pass the path to a specific workspace folder or its `mta_config.json` directly:
   ```bash
   npm run update:modules -- ../app-alpha-workspace
   # or absolute path:
   npm run update:modules -- "C:\projects\menditect\app-alpha-workspace"
   ```

3. **Update Multiple Specific Workspaces:**
   You can provide multiple workspace paths in a single command:
   ```bash
   npm run update:modules -- "../app-alpha-workspace" "../app-beta-workspace"
   ```

4. **Update All Registered Workspaces (`--all` / `-a`):**
   To update Marketplace modules across **all** registered workspaces in your Central Tools Hub in one batch:
   ```bash
   npm run update:modules -- --all
   # Dry-run check for all workspaces:
   npm run update:modules -- --check --all
   ```
   The sync engine automatically discovers all candidates from `.mxcli/workspaces.json`, deduplicates by underlying Mendix project directory, checks module versions per application, and updates them sequentially with clear progress banners (`[1/N] === AppName ===`).

5. **Target via Environment Variable:**
   ```bash
   # Target specific workspace via MTA_CONFIG_PATH
   MTA_CONFIG_PATH=../app-alpha-workspace/mta_config.json npm run update
   ```

## Model Context Protocol (MCP) Servers & Linter Architecture

The Agentic Test Workspace orchestrates specialized MCP servers and a deterministic Linter Engine across external AI IDEs and Mendix Studio Pro MAIA:

| Component | Transport & Execution | Description & Purpose | Authentication |
| :--- | :--- | :--- | :--- |
| **`mta`** | Stdio (via `mta-proxy.js`) or HTTP | Connects to the Menditect MTA Cloud / Server platform for persistent test suites, test cases, variation matrices, and backend assertions. | Bearer Token (`MTA_MCP_AUTH_HEADER` in `.env`) |
| **`mta_plugin`** | Stdio (via `mta-proxy.js` &rarr; HTTP `/plugin/mcp`) | Connects to the running Mendix application runtime for sub-second, in-memory exploratory test execution (`execute-testcase`). | Bearer Token (`PLUGIN_MCP_TOKEN` in `.env`) |
| **`StudioPro`** | Stdio (via `mta-proxy.js` &rarr; HTTP port 7782) | Optional live model inspection server embedded in Mendix Studio Pro 11.12+. | None |
| **`mta-lint.mjs` / `mta-linter` Extension** | • **External IDEs:** Direct Node.js CLI (`node tools/mta-lint.mjs`)<br>• **Studio Pro MAIA (11.12+):** Bundled TypeScript Studio Pro Web Extension in `Menditect_AgenticTestSkills.mxmodule` | Canonical 6-section test plan linter, safety gate enforcement (`pre_exec_check`, `pre_build_check`), Gate 2 placement staging, SHA-256 plan locking, and post-build semantic smoke auditing. | Local File System / Studio Pro `AppFilesApi` |

### Built-in `mta-linter` Studio Pro Extension for Mendix MAIA (Mendix 11.12+)

While external AI coding assistants (Cursor, VS Code, Claude Code, Antigravity) execute `node tools/mta-lint.mjs` directly via CLI, **Mendix Studio Pro MAIA (11.12+)** runs inside Studio Pro without direct shell/Node.js access. To provide identical deterministic enforcement in MAIA with **zero external processes to start**:

* **Bundled in `Menditect_AgenticTestSkills.mxmodule` (Component `305457`):**
  - The `mta-linter` TypeScript Studio Pro Web Extension is packaged directly inside `Menditect_AgenticTestSkills.mxmodule`.
  - It starts automatically whenever Studio Pro opens the Mendix project (no batch files, background Node servers, or localhost ports required).
* **Automatic Skill Sync & Zero-Setup `mta_config.json` Bootstrap:**
  - On Studio Pro startup, the extension automatically copies/updates all skills in `skillssource/_modules/menditect_agentictestskills/` and ensures `skillssource/AGENTS.md`, `AGENTS.md`, and `mta_config.schema.json` are present via `mendix.AppFilesApi`.
  - If the module was installed directly from the Mendix Marketplace without running `npm run setup`, MAIA calls `get_config()` (which auto-detects the project name and `.mpr` path via `mendix.ProjectManagerApi`) and initializes `<MendixProjectDir>/mta_config.json` via `update_config({ create_if_missing: true, updates })`.
* **Dedicated Menditect Test Plan Directory (`menditect-output/execution-plans/`):**
  - Across all Mendix versions `>= 11.12` (including Mendix 11.16+ Plan Mode), MAIA passes `plan_content` with `persist: true` to `lint_plan`, which validates and writes Menditect test plans to `<MendixProjectDir>/menditect-output/execution-plans/EP_*.md` and records the gate ledger at `<MendixProjectDir>/menditect-output/.mta-gate-ledger.json`.
  - This ensures **Menditect test plans** (`menditect-output/execution-plans/`) are always cleanly separated from **MAIA application build plans** (`maia/plans/`).
* **10 Native MAIA Tools (`mendix.ExternalAIToolRegistryApi`):**
  1. `get_config`: Read active workspace configuration from `mta_config.json` (or auto-detect project defaults if missing).
  2. `update_config`: Initialize or deep-merge updates into `mta_config.json` and validate against schema invariants.
  3. `lint_plan`: Lint a 6-section Execution Plan (`EP_*.md`) and persist it to `menditect-output/execution-plans/` when `persist: true`.
  4. `pre_exec_check`: Verify on-disk plan existence, status (`AUTO_APPROVED` / `APPROVED`), and gate ledger receipt before `MTA_plugin.execute-testcase`.
  5. `stage_placement`: Stage target configuration, suite, and Playwright options in `.mta-gate-ledger.json` before Checkpoint 2.
  6. `pre_build_check`: Verify Gate 1 and Gate 2 human approval before mutating MTA Cloud/Server assets.
  7. `lock_plan`: Compute SHA-256 hash and lock a Red bug-reproduction test plan (`PAT-124`).
  8. `verify_lock`: Verify that a locked test plan's assertions have not been tampered with during code repair (`ANTI-78`).
  9. `smoke_audit`: Run the 4-phase semantic smoke audit comparing the approved plan against MTA server JSON payloads.
  10. `list_plans`: List all discovered `EP_*.md` test execution plans in `menditect-output/execution-plans/`.

## Configuration Contract (`mta_config.json`) & Resolution Hierarchy

All Menditect Agentic Test Skills strictly consume `mta_config.json` as the primary **Single Source of Truth (SSOT)** for workspace paths, MTA server endpoints, model discovery sources, and application instances. Sensitive authentication tokens (`MTA_MCP_AUTH_HEADER`, `PLUGIN_MCP_TOKEN`) are securely maintained in `.env`.

  "plugin_mcp_url": "http://localhost:[Port]/plugin/mcp",

### Core Properties Reference

| Field | Type | Description |
| :--- | :--- | :--- |
| `mta_base_url` | string (URI) | **(Required)** Base URL of the Menditect Test Automation web portal (e.g. `https://mta-instance.mendixcloud.com`). Used for clickable web navigation links. |
| `mcp_endpoint` | string (URI) | **(Required)** MCP endpoint URL for the MTA primitive tools server (`[mta_base_url]/primitivetools/mcp`). |
| `application_name` | string | **(Required)** Name of the target Mendix application in MTA. Eliminates manual application disambiguation prompts. |
| `execution_plans_dir` | string | **(Required)** Directory where active Execution Plans (`EP_*.md`) are stored and updated in-place. |
| `execution_plan_collapsible` | boolean | Whether to format execution plans with collapsible `<details>` HTML tags (default: `true` for VS Code/GitHub) or flat Markdown headers (`false` for Claude Desktop/pure markdown). |
| `exploratory_execution_mode` | string (`"auto_execute"` \| `"prompt_approval"`) | **(Default: `"auto_execute"`)** Execution strategy for Option A in-memory unit tests on the MTA Plugin (`Rollback = Yes`). `"auto_execute"` generates the Execution Plan (`EP_*.md`) on disk and executes in 1 turn without halting at Checkpoint 1. `"prompt_approval"` halts at Checkpoint 1 for manual sign-off before dispatching. |
| `mendix_project_dir` | string | **(Required)** Absolute path to the target Mendix project folder containing the app model. |
| `mendix_mpr_path` | string | Absolute path to the Mendix `.mpr` project file used by `mxcli`. |
| `mta_auth_header` | string | *(Deprecated)* HTTP Authorization header (`Bearer <session_token>`) for authenticating with MTA server. Stored in `.env` as `MTA_MCP_AUTH_HEADER`. |
| `plugin_mcp_url` | string (URI) | Local runtime plugin MCP endpoint (`[ApplicationRootUrl]/plugin/mcp`) for sub-second in-memory exploratory test execution. |
| `documentation_url` | string (URI) | Base URL of the Menditect MTA documentation site (default: `https://documentation.menditect.com`). Used for dynamic retrieval of official guides and `llms.txt`. |
| `llms_txt_url` | string (URI) | Explicit override URL for the `llms.txt` documentation index (defaults to `${documentation_url}/llms.txt`). |
| `plugin_mcp_token` | string | *(Deprecated)* Authorization header (e.g. `Bearer 1`) for the runtime plugin MCP endpoint. Stored in `.env` as `PLUGIN_MCP_TOKEN`. |
| `app_instances` | array | Discovered application runtime instances with `name`, `token`, `mtaUrl`, `runtimeUrl`, `pluginUrl`, `pluginToken`, and `pluginPort`. |
| `default_app_instance` | string | Name of the primary default application runtime instance. |
| `default_app_instance_token` | string (UUID) | MTA Application Instance Token used for executing tests via `ExecuteTest`. Eliminates manual prompts. |
| `model_source` | string | AST discovery mechanism: `"mxcli"` (headless offline `.mpr` inspection) or `"studiopro"` (Studio Pro live MCP server). |
| `execution_plans_archive_dir` | string | *(Deprecated)* Formerly used for archiving superseded plans. Replaced by in-place plan revisions tracked in Git. |
| `workspace_type` | string | Mode where the agent runs: `"clone_root"` (isolated tools workspace), `"mendix_project"` (direct Mendix project), or `"custom"`. |
| `skills_style` | string | Installation style: `"standard"` (project-level `skills/`) or `"mendix_module"` (Mendix 11.12+ `skillssource/_modules/menditect_agentictestskills`). |

### Automated Application Instance Token Resolution (`ExecuteTest`)

Executing test suites or test cases via the `ExecuteTest` MCP tool requires a valid `ApplicationInstanceToken`:
1. **Targeted Instance**: If the user targets a specific environment by name (e.g., *"run test on local"* or *"use instance Markus demo"*), the agent searches `app_instances[]` for a matching `name` and extracts its `token`.
2. **Default Instance**: Otherwise, the agent automatically uses `default_app_instance_token` from `mta_config.json`.
3. **Environment Variable Fallback**: If missing in `mta_config.json`, the agent falls back to `MTA_APPLICATION_INSTANCE_TOKEN` in `.env`.
4. **Interactive Prompt**: The agent prompts the user only if no instance token can be resolved across any source.

### Strict Configuration Resolution Hierarchy

When resolving configuration settings, AI agents must evaluate sources in this strict order of precedence:

1. **`mta_config.json` (Priority #1 - SSOT)**: Evaluates `mcp_endpoint`, `mta_base_url`, `app_instances`, `default_app_instance_token`, `mendix_mpr_path`, and `execution_plans_dir`. Backward-compatible fallback for `mta_auth_header`.
2. **Project `AGENTS.md`**: Reads `- ** MTA Url: <URL> **` and instance token mappings (`- [Name] (Default): <Token>`).
3. **Environment Variables (`.env` / process env)**: Primary secure storage for authentication headers (`MTA_MCP_AUTH_HEADER`, `PLUGIN_MCP_TOKEN`) and environment overrides (`MTA_MCP_ENDPOINT`, `PLUGIN_MCP_URL`, `MTA_APP_INSTANCE_TOKEN`, `MENDIX_MPR_PATH`).
4. **IDE Settings (`.vscode/settings.json`, `.cursor/mcp.json`)**: Reads `MTA_BASE_URL` and `MENDIX_PROJECT_PATH`.
5. **Session State (`mta_state.json`)**: Reads `mta_base_url`.
6. **Interactive Prompt**: Prompts the user on turn 1 only if a required setting is absent across all configuration sources.
